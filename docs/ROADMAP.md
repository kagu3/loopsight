# ロードマップ

全体の構想と前提は [VISION.md](VISION.md) を参照。ここでは段階 1（中核部分＋MCP）の作り方を中心にまとめる。

## 段階 1：中核部分＋MCP

**状態：** M0〜M5 を実装済み。残っているのは、実際に Claude Code に登録しての試用と、書き出したファイルを Web 版に読み込めるかの確認（ログインが必要なので人が行う）。

### 設計方針

- **中核部分と MCP を分ける。** `src/core` はモデルの保持・変換・実行を担当し、MCP には依存しない。`src/mcp` は中核部分を MCP ツールとして公開するだけの薄い層にする。段階 2 の Web 画面は `src/core` をそのまま再利用する。
- **モデルの正本は ModelJSON にする。** 作業中のモデルは、作業フォルダ（例：`models/`）に `<名前>.json` として保存する。メモリ上だけで持たない。こうしておくと、人がファイルを直接見られるほか、段階 2 の画面はファイルの変更を監視するだけで AI の変更を反映できる。
- **実行時は毎回 ModelJSON から `simulation` の Model を作り直す。** 状態を二重に持たないためで、変換コストは小さい。
- **AI に返す結果は小さくまとめる。** 時系列データをすべて返すと文脈を圧迫するので、最終値、最小値と最大値、間引いた時系列を基本にする。全データは CSV ファイルに書き出す。
- **insightmaker.com にはアクセスしない**（利用規約）。

### 技術選定（案）

- TypeScript、Node 20 以上、ES Modules
- `@modelcontextprotocol/sdk`（stdio トランスポート）
- `simulation@9`（JSDoc の型定義が同梱されている）
- `zod`（ツール入力の検証）
- `vitest`（テスト）

### マイルストーン

#### M0. プロジェクトの雛形
- `package.json`、`tsconfig.json`、ビルドとテストのスクリプト
- 何もしない MCP サーバーが Claude Code から認識される状態にする（`.mcp.json` の例も用意する）

#### M1. 中核部分：モデルの保持と変換
- ModelJSON の読み込みと保存（作業フォルダ内のファイル）
- `.InsightMaker` ファイルの読み込み（ルートタグを `InsightMakerModel` に置き換えてから `loadInsightMaker` を呼び、`toModelJSON` で ModelJSON に変換）
- 要素の追加、変更、削除（ストック、フロー、変数、コンバーター、リンク）
- 検証（`loadModelJSON` が出すエラーを、AI が読んで直せる形で返す）
- テスト：公開されている ModelJSON のサンプル（`simulation` に同梱）で往復が一致すること

#### M2. 中核部分：シミュレーション
- 実行して結果を要約する（最終値、最小値と最大値、間引いた時系列）
- 結果を CSV に書き出す
- パラメータを一時的に上書きして実行する（ファイルは変えない）
- パラメータを振って比較する（感度分析、シナリオ比較）

#### M3. MCP ツール
最初に用意するツールの案：

| ツール | 内容 |
|---|---|
| `list_models` | 作業フォルダのモデル一覧 |
| `create_model` | 空のモデルを作る（名前、シミュレーション設定） |
| `import_model` | `.InsightMaker` または ModelJSON ファイルを取り込む |
| `export_model` | Insight Maker の Web 版に読み込める `Model.json` を書き出す |
| `get_model` | ModelJSON 全体、または要約（要素一覧と式）を返す |
| `upsert_elements` | 要素をまとめて追加・更新する |
| `remove_elements` | 要素を削除する（つながっているリンクやフローも扱う） |
| `set_simulation` | 開始時刻、期間、刻み幅、解法、時間単位を設定する |
| `validate_model` | エラーと警告を返す |
| `run_simulation` | 実行して要約を返す。必要なら CSV に保存する |
| `sweep_parameter` | パラメータを振って、指定した要素の結果を比較する |

#### M4. 簡易レイアウト
- 座標がない要素に、重ならない程度の座標を付ける（ストックを横に並べ、変数をその周りに置く程度）
- 目的は、書き出したファイルを Insight Maker の Web 版に読み込んだとき、要素が重ならないこと。本格的な自動配置は段階 2 でやる

#### M5. 仕上げ
- README に使い方を書く（Claude Code への登録方法、ツール一覧、Web 版との受け渡し手順）
- 実際に Claude Code から、モデルを作る → 実行する → 書き出す、までを通して試す
- 書き出したファイルを Insight Maker の Web 版に読み込めるか確認する（ログインが必要なので、人が手で確かめる）

### 段階 1 の完了条件

- Claude Code から、言葉でモデルを作り、実行し、パラメータを振って比較できる
- Insight Maker の Web 版で作ったモデル（`.InsightMaker` / ModelJSON）を読み込んで分析できる
- 作ったモデルを Web 版に読み込める形で書き出せる

## 段階 2：見るための Web 画面

作業フォルダの ModelJSON を監視して、図とグラフを表示する。AI が MCP でモデルを変えると、画面がその場で変わる。画面からは編集しない（段階 3）。

### 設計方針

- **ビューアは MCP サーバーとは別のプロセスにする。** `npm run viewer`（`insight-maker-viewer`）で起動する。MCP サーバーとは作業フォルダのファイルだけでつながる。どちらか片方だけでも動く。
- **サーバーは Node 標準の `http` で書き、`src/core` を再利用する。** 実行もサーバーで `runModel` を使う。ブラウザには結果の数値だけを送るので、エンジンをブラウザに積まない。
- **変更は Server-Sent Events で知らせる。** サーバーが作業フォルダを `fs.watch` で監視し、変わったモデル名をブラウザへ送る。ブラウザはそのモデルを取り直す。
- **`127.0.0.1` だけで待ち受ける。** 外部からは見えない。Host ヘッダーも確かめ、DNS リバインディングで別のサイトから読まれないようにする。
- **画面は React と React Flow（MIT）で描く。** フローは「弁」のノードを真ん中に置き、出元 → 弁 → 行き先の 2 本の線で描く。リンクが弁につながれるようにするため。モデルの外の端は雲のノードにする。
- **座標はモデルにあればそれを使い、ない要素があれば自動配置にする。** 自動配置は dagre（MIT）で、フローの流れを左から右に並べる。画面のボタンで、座標があっても自動配置に切り替えられる。自動配置の結果はファイルに書き戻さない。
- **グラフは Recharts（MIT）で描く。** 表示する要素は、モデルのグラフ設定（`visualizations`）の最初のものを使い、なければストックすべてにする。画面で切り替えられる。
- **フロントエンドは `web/` に置き、Vite でビルドして `dist/web` に出す。** 依存ライブラリは画面に同梱するので devDependencies に入れる。

### マイルストーン

- **V1. サーバー：** モデル一覧、モデルと実行結果と検証結果を返す API、変更の通知、静的ファイルの配信
- **V2. 図：** ストック、フロー（弁と雲）、変数、コンバーター、リンクを描く。自動配置。要素を選ぶと式などを横に出す
- **V3. グラフ：** 実行結果の時系列グラフ。表示する要素の切り替え。検証エラーの表示
- **V4. 仕上げ：** MCP でモデルを変えると画面が変わることを確かめる。README に使い方を書く

## 段階 3：編集できる Web 画面

画面からの編集も同じ ModelJSON ファイルに書き戻し、AI と人が同じモデルを扱えるようにする。まず「AI が作ったモデルを人が少し手直しする」場面をまかなう E1・E2 と、その安全策 E4 を作る。要素の追加や削除（E3）はそのあと。

### 設計方針

- **編集は `src/core` の `upsertElements` を通す。** MCP の `upsert_elements` と同じ処理なので、画面から直しても AI から直しても同じ検証が通る。足りないリンクの自動追加も同じ。
- **書き込みは 1 つの API にまとめる。** `POST /api/models/:name/edit` に、要素の変更（`upsert_elements` と同じ形）を送る。式の変更も、位置の変更（`display.coordinates` など）も同じ形になる。
- **衝突は版で見つける。** モデルを返すときにファイルの中身のハッシュを「版」として付ける。書き込みのときに画面が持っている版を送り、ファイルの版と違えば（AI などが先に変えていれば）書き込まずに 409 を返す。画面は最新を読み直して、そのことを知らせる。黙って上書きはしない。
- **元に戻すはサーバーで持つ。** 画面から書き込むたびに、書き込む前の中身を覚えておく（モデルごとに 50 回分、メモリの中だけ）。元に戻すときは、ファイルがその書き込みの直後のままの場合だけ戻す。そのあと AI などが変えていたら、戻さずに知らせる。
- **書き込みの API は、ほかのサイトから呼べないようにする。** Host ヘッダーの確認に加えて、`Origin` がビューア自身であること、独自のヘッダー（`X-IM-Viewer`）と `Content-Type: application/json` があることを求める。独自のヘッダーがあるとブラウザは事前の確認（CORS のプリフライト）をし、ビューアはそれに応えないので、ほかのサイトからは送れない。
- **E1 値と式の編集：** 選んだ要素の詳しい情報の欄で、式（流量）、初期値、単位、負にしない、説明を直す。数字だけなら数値、それ以外は式として保存する。コンバーターは表（入力と出力の組）も直せる。状態と遷移は段階 1 と同じく編集しない。
- **E2 配置の編集：** 図の要素と雲をドラッグで動かし、離したときに位置を保存する。弁は両端の真ん中についてくる。自動配置で表示しているときに動かすと、表示している配置をまとめて保存する（座標のない要素が残らないように）。

### マイルストーン

- **E4. 書き込みの API（済み）：** 編集、元に戻す、版による衝突の検知、ほかのサイトからの書き込みの拒否
- **E1. 値と式の編集（済み）**
- **E2. 配置の編集（済み）。** 左や上にはみ出したら全体をずらして保存する
- **E3.（これから）要素の追加、削除、名前の変更、線でつなぐ操作**
