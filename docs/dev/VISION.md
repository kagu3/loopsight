# 構想と前提

このプロジェクトが目指すものと、そこに至るまでに調べてわかった前提をまとめる（調査日：2026-10-15）。

## 目指すもの

（方針を決めた日：2026-10-16）

### ミッション

システムダイナミクス（SD）を使える人がシミュレーションするだけでなく、SD を知っている人が SD を知らない人に、シミュレーションを通じて SD が問題解決に役立つ道具だと分かってもらい、SD を組織に根付かせられるようにする。

### ミッションを達成するために

ビューアは実際の問題解決に使えるものにする。SD を知らない人でも、ビューアを見れば問題解決につながる情報が一目で分かるようにする。

### 今の課題と解決の方針

今でもシミュレーションはできていて、ビューアも動いている。ただ、一目で言いたいことが分かる資料にはなっていない。資料としての分かりやすさを広げていく。

### 最初の目標

SD を知っている人が、SD を知らない人に問題を定義し、解決案を示せるようにする。説明なしで分かる資料にするのは、その次の段階にする。

作業画面と正式な提案資料の役割は、次のように分ける。

- **作業画面**：モデルを作る人が使う。シナリオの比較、実際のデータの重ね描き、ループの強調がある。会議でその場で説明するときも、この画面を映して説明する
- **正式な提案資料**：決定権がある人向けの資料は、モデルの結果を元に、このプロジェクトの外で（PowerPoint などで）作る。このプロジェクトでは作らない

その先の案は [IDEAS.md](IDEAS.md)（まだ決まっていない）

### 操作の指針

「何ができるかは、人と AI で同じにする」などの操作の指針は、外から PR を送る人にも守ってほしいので [CONTRIBUTING.md](../../CONTRIBUTING.md#守ってほしい決まり) に移した。

## 3 段階の構想

| 段階 | 内容 | 状態 |
|---|---|---|
| 1. 中核部分＋MCP | モデルを保持して ModelJSON で読み書きし、`simulation` で実行する中核部分と、それを操作する MCP ツール | 実装済み |
| 2. 見るための Web 画面 | 中核部分と同じモデルを表示し、AI の変更をその場で図とグラフに反映する。図の自動配置もここで入れる | 実装済み（`npm run viewer`） |
| 3. 編集できる Web 画面 | 必要になったら、人が手で直せるようにする | 実装済み（式などの編集、名前の変更、配置の保存、要素の追加・削除、線を引く、元に戻す） |

段階 1 だけで終われば「Insight Maker 用の MCP」になり、2 と 3 まで進めば「AI 前提の自作モデリングツール」になる。どちらに進んでも、段階 1 の成果は無駄にならない。

## 調査でわかった前提

### Insight Maker 本体について

- **公開されている Web API はない。** 公式に用意されている、プログラムから使う手段は次の 3 つだけ。
  - In-Page Action API：開いているモデルの中（ボタンなど）で動く JavaScript。外部からは呼べない
  - npm パッケージ [`simulation`](https://github.com/scottfr/simulation)
  - R パッケージ sdbuildR
- **利用規約（[/termsofuse](https://insightmaker.com/termsofuse)）が自動アクセスとスクレイピングを禁止している。** **このプロジェクトから insightmaker.com には一切アクセスしない。**
- **現行の Web アプリはオープンソースではない。** 公開されているのはエンジンだけ。旧版（2016〜2018 年ごろ、ExtJS と mxGraph を使用）のソースは scottfr/insightmaker のフォークに残っている。ただし独自ライセンス（AGPL に加えて、画面に InsightMaker.com のクレジットを大きく表示する義務がある）で、ExtJS と mxGraph は別ライセンスが必要になる。そのため使わない。

### エンジン `simulation` について（v9.0.0 で確認）

- Insight Maker 公式のシミュレーションエンジン。Node でもブラウザでも動く。ライセンスは **AGPL**。
- `loadInsightMaker`（XML の読み込み）、`loadModelJSON`、`toModelJSON` がある。**Insight Maker 形式の XML を書き出す機能はない。** このプロジェクトは ModelJSON だけを読み書きする（はじめは `loadInsightMaker` で `.InsightMaker` を取り込んでいたが、#1 で外した）。
- **エージェントベースのモデル（Population）は ModelJSON に対応していない。**
- コードで作ったモデルは、要素の座標がすべて `[0,0]` になる。図として見せるには配置が必要になる。

### ファイル形式について

- [ModelJSON](https://github.com/scottfr/modeljson)（CC0）は、「LLM が生成しやすいこと」を設計目標の一つにした JSON 形式。ストック、フロー、変数、リンク、コンバーター、状態、遷移に対応している。
- **Insight Maker の Web 版は ModelJSON を読み書きできる**（Import/Export メニュー）。はじめは、Web 版との受け渡しを ModelJSON ファイルの手でのインポート・エクスポートで行う想定だった。今はビューアで見て確かめられるので、Web 版とのやりとりは想定していない。

## 制約と方針

共通のデータ形式（ModelJSON）、insightmaker.com に自動でアクセスしないこと、ライセンス（AGPL）などの決まりは、[CONTRIBUTING.md](../../CONTRIBUTING.md#守ってほしい決まり) に移した。

## 設計の要点

段階 1〜3 の設計の記録（ROADMAP.md、今は消した）のうち、今も守っている考え方を残す。

- **モデルの正本は作業フォルダの ModelJSON ファイルにする。** メモリの上だけで持たない。人がファイルを直接見られ、ビューアはファイルの変更を監視するだけで AI の変更を出せる
- **実行のたびに ModelJSON から `simulation` のモデルを作り直す。** 状態を二重に持たないため
- **AI に返す結果は小さくまとめる。** 最終値、最小値と最大値、間引いた時系列を基本にし、全データは CSV に書き出す
- **ビューアは MCP サーバーとは別のプロセスにする。** 作業フォルダのファイルだけでつながり、どちらか片方だけでも動く。`127.0.0.1` だけで待ち受け、Host ヘッダーも確かめる
- **画面からの編集も `src/core` の `upsertElements` を通す。** MCP の `upsert_elements` と同じ検証が通る
- **書き込みの衝突は版で見つける。** ファイルの中身のハッシュを版にし、画面の版とファイルの版が違えば書き込まずに知らせる。黙って上書きしない
- **元に戻すはサーバーで持つ。** 画面から書き込むたびに、書き込む前の中身を覚えておく（モデルごとに 50 回分、メモリの中だけ）。ファイルが書き込みの直後のままのときだけ戻し、そのあと AI などが変えていたら戻さずに知らせる
- **書き込みの API は、ほかのサイトから呼べないようにする。** `Origin`、独自のヘッダー（`X-IM-Viewer`）、`Content-Type: application/json` を求める。独自のヘッダーがあるとブラウザは事前の確認（CORS のプリフライト）をし、ビューアはそれに応えないので、ほかのサイトからは送れない
- **図の配置は、決まった手順の自動配置より、AI が図を見ながら直す。** `layout_model` でたたき台を作り、`view_diagram` の画像と数字の一覧を見て、`upsert_elements` の `display` で直す
