# sample のモデル

システム思考を学ぶための sample のモデル。システムダイナミクス（SD）を知っている人が、知らない人に見せて「問題を解くのに使える」と分かってもらうための教材にする。

どの sample も、身近な仕事の話を小さなモデルにしてある。図でフィードバックループ（R：強めるループ、B：釣り合わせるループ）を見て、グラフで動きを確かめ、シナリオで「どこを変えると効くか（てこ）」を比べる。

## 学ぶ順

上から順に見ると、前の sample で学んだことの上に、新しいことを 1 つずつ足していける。

### 0 コーヒーが冷める

- 学ぶこと：釣り合わせるループ（B）。差が縮むほど変化がゆっくりになり、目標（部屋の温度）に近づいて落ち着く。物理の法則（ニュートンの冷却の法則）なので、議論の余地がない。最初に見せる
- フォルダ：[0_コーヒーが冷める](0_コーヒーが冷める/)（coffee-cooling.json）

### 1 成長の限界

- 学ぶこと：強めるループ（R）と、R と B の組み合わせ（S 字の動き）
- フォルダ：[1_成長の限界](1_成長の限界/)（limits-to-growth.json）

### 2 うまくいかない解決策

- 学ぶこと：遅れ。目先はよくなり、後で悪くなる
- フォルダ：[2_うまくいかない解決策](2_うまくいかない解決策/)（fixes-that-fail.json）

### 3 問題のすり替わり

- 学ぶこと：対症療法が、根本の解決の力を奪う
- フォルダ：[3_問題のすり替わり](3_問題のすり替わり/)（shifting-the-burden.json）

### 4 エスカレート

- 学ぶこと：2 者の B がつながると、全体が R になる。R は、増えるほど増え方が速くなる（0 のコーヒーの B と見比べる）
- フォルダ：[4_エスカレート](4_エスカレート/)（advertising-war.json）

### 5 成長と投資不足

- 学ぶこと：1〜3 の組み合わせ（口コミの R、設備ができるまでの遅れ、すぐ効くほうに逃げる）。目標のなし崩しで投資が遅れ、伸びるはずだったお客を自分で失う
- フォルダ：[5_成長と投資不足](5_成長と投資不足/)（growth-and-underinvestment.json）

### 6 ブルウィップ効果

- 学ぶこと：遅れが何段も重なると、振動する（ビールゲーム）。大きいので最後に見せる
- フォルダ：[6_ブルウィップ効果](6_ブルウィップ効果/)（bullwhip.json、対策を比べる bullwhip-countermeasures.json）

## 使い方

sample は npm パッケージには入っていない。[GitHub のリポジトリ](https://github.com/kagu3/loopsight) から取る（`git clone` するか、「Code」→「Download ZIP」で落として展開する）。

1. sample のフォルダ（例：`examples/1_成長の限界/`）を、フォルダごと作業フォルダにコピーする。作業フォルダは、MCP サーバーとビューアに渡しているフォルダ（[はじめての手順](../docs/getting-started.md) のとおりなら、ホームフォルダの中の `loopsight-models`）
2. ビューアのモデルの一覧に、フォルダと一緒に出てくる。開くと、図、グラフ、シナリオが見られる
3. Claude に、次のように頼める

> 1_成長の限界 のモデルの R と B のループを説明して、図で目立たせて。

> このモデルのシナリオを、何も変えない実行と比べて、何が効いているのか説明して。

モデルの説明（ビューアと `get_model` で読める）は、最初の段落が要点（問題と、てこ）の短い概要で、ビューアの上の帯の 2 行目にも出る。そのあと「どんな問題か → どんな構造か → どんな動きになるか → てこはどこか」の順に書いてある。グラフで、シナリオと重ねて出る何も変えない実行の線には、何を表す線かの名前（例：2 の「残業で取り戻す（今のやり方）」）が付いている。数字の根拠と単純化したことは `【数字と単純化について】` に、値を振ったときの結果などの細かい話は、最後の `【もっと詳しく】` にある。

## 出典と、数字について

1〜5 は、ピーター・センゲ『学習する組織』（原題 *The Fifth Discipline*）の「システムの原型」を、6 は同じ本のビールゲームをもとにした、このプロジェクトで作ったモデル。本の文章や図は写さず、筋書きだけを借りて、同じ構造の仕事の話に置き換えている。0 は物理の法則（ニュートンの冷却の法則）をもとにしている。

1〜6 の数字は、動きの形を見せるための仮の値で、実際の会社や仕事の値ではない。0 だけは例外で、物理の法則のモデルなので、実測にもとづく値を使っている（値の根拠は、そのモデルの説明に書いてある）。どの sample も、分かりやすくするために話を単純にしてある（何を省いたかは、各モデルの説明に書いてある）。

0 のふつうのマグの冷めやすさ（0.019/分）と初めの温度（98.2 ℃）は、Stan Wagon がマグに入れた熱湯の温度を測った記録（R の [mosaicData](https://github.com/ProjectMOSAIC/mosaicData) パッケージのデータ CoolingWater）から決めた。記録のファイルは置いていない。

## sample を足す・直すときの決まり

### 置き方

- `examples/<番号>_<名前>/<英数字>.json` に置く（例：`examples/1_成長の限界/limits-to-growth.json`）。番号は上の「学ぶ順」の番号
- 実際のデータ（`<モデル名>.data.csv`）があれば、モデルと同じフォルダに置く
- 要素の名前、説明、シナリオは日本語で書く。モデルのファイル名は英数字と `_` `-` にする（例：`limits-to-growth.json`）
- sample を足したら、上の「学ぶ順」に項目を足し、「学ぶこと」と、フォルダへのリンクとモデルのファイル名を書く

  ```markdown
  - フォルダ：[1_成長の限界](1_成長の限界/)（limits-to-growth.json）
  ```

### 中身の決まり

- **簡単で、理論に穴がない（批判されにくい）こと。** ただし抽象的すぎず、仕事の具体的な話にする
- **式にするのは、裏付けのある関係だけ。** 物理や算数で決まること、研究で何度も確かめられたこと
- **人の判断は、判断の決まりは図に入れてよいが、どれだけ強く反応するかはシナリオのつまみにする。** 人の間違った反応と、てこ（効く打ち手）はシナリオで見せる
- **説明の最初の段落は、見出しなしの 60 文字以内の概要にする。** 問題と、てこの要点を書く。ビューアの上の帯の 2 行目に出るので、ここだけ読めば要点が分かるようにする。帯には最初の段落（最初の空行まで）が 1 行で出るので、概要のあとに空行を入れて `【どんな問題か】` と分ける。60 文字は、空白も 1 文字に数え、段落の中の改行は空白 1 つに数える（帯に出るとおり）。見本（3 問題のすり替わり）：

  ```text
  売上の不足を営業で埋め続けると、品質を直す合図とお金が消え、2 年後に崩れる。てこは不足を品質の改善に回すこと。

  【どんな問題か】
  ある製品の売上が目標（80 百万円/月）に届いていない。…
  ```

- **概要のあとの見出しは `【どんな問題か】` → `【どんな構造か】` → `【どんな動きになるか】` → `【てこはどこか】` → `【数字と単純化について】` → `【もっと詳しく】` の順に、それぞれ行の頭に置く。** 本文には要点の数字だけを書く
- **`【数字と単純化について】` には、数字が仮の値か根拠つきか、単純化したこと、出典を書く。** ふつうは「動きの形を見せるための仮の値」と書く。0 のように実測にもとづく値を使うときは、その根拠を書く。何を省いたか、どの本や研究をもとにしたかも書く
- **感度分析の結果（値を振るとどう変わるか）や、細かい根拠は、最後の `【もっと詳しく】` に書く。** SD を知らない人は、ここまで読まなくてよいようにする
- **説明の要の数字を変えたら、`tests/examples-numbers.test.ts` の表も直す。** 説明に書いた結果の数字のうち、要のもの（1 つのモデルで 2〜4 つ）を、表で結果と照らしている。sample やモデルを足したら、そのモデルの行も足す（行が 2 つより少ないか 4 つより多いと、テストが落ちる）
- **てこのシナリオを 1 つ以上入れる。** 対策は図に足さず、シナリオか別のモデルで比べる
- **シナリオで変えるのは数字だけ（式を入れない）。** 式はシナリオの表にそのまま出て、長くて省略される。式で変えたいとき（12 か月目から変える、など）は、数字のつまみになる変数をモデルに足す（例：4 の「A社が競り合いをやめる週」。何も変えない実行では期間より後の 100 にしておき、シナリオで 12 にする）
- **何も変えない実行には、その線が何を表すかの名前と説明を付ける**（`set_scenarios` の `baseline`。例：2 の「残業で取り戻す（今のやり方）」、6 の対策を比べるモデルの「対策なし」）。名前は凡例で見切れないよう短くする。説明やシナリオの説明では「元のモデル」と呼ばず、付けた名前か、自然な言い方（「今のままなら」など）で書く
- **説明にしか書いていない結果のうち、グラフで確かめてほしいものは、シナリオとして保存する。** グラフが見にくくならないよう、シナリオは 1 つのモデルで多くても 4 つにする（何も変えない実行を除く）
- **主なループの読み方を、注釈（`set_annotations`）で図の中に 1〜2 つ置く。** 0 の「Bの読み方」と同じ形で、ループの記号と、何が増えると何が起きるかを 1 文で書く。かっこの中は、ループの種類か呼び名にする（例：「R（口コミ）：使っている人が増えるほど、誘われて使い始める人も増える」）。置いたら `view_diagram` で、重なりや、線が注釈の上を通るところがないか確かめる
- **すべてのリンクに極性（`behavior.polarity`）を入れ、時間がたってから効くつながりには遅れの印（`display.delay`）を付ける。** `find_loops` で原型どおりの R と B が見つかるようにする
- **図に重なりや、線が要素の上を通るところがない**（`view_diagram` の一覧が空）
- **本の文章・図・固有名は写さない。** 筋書きは使ってよい。実在の会社や国の話は、同じ構造の仕事の話に置き換える。出典として本の名前を書くのはかまわない

### テストで確かめていること

`npm test`（`tests/examples.test.ts`）が、`examples/` の下のすべての ModelJSON（`*.json`）について次を確かめる。1 つでも守らないと、どの sample のどの決まりに反したかを出して落ちる。この README のリンク切れは `tests/docs-links.test.ts` が確かめる。

- 置き方が `examples/<番号>_<名前>/<英数字と _ ->.json` になっている
- 検証（`validate_model`、試しの実行あり）でエラーも警告もない
- モデルの説明（`description`）があり、最初の段落が見出しなしの 60 文字以内（空白も数える）の概要で、そのあと空行をはさんで、見出しが上の「中身の決まり」の順に並んでいる
- 何も変えない実行に、名前（既定の「いまのまま」でないもの）と説明がある。説明・シナリオの説明・注釈・要素の説明に「元のモデル」がない
- すべてのリンクに極性（+ か −）がある。`find_loops` で R か B か決まっていないループがない
- シナリオが 1 つ以上あり、何も変えない実行もシナリオもすべて実行できる
- シナリオの値がすべて数字（式でない）。1 のシナリオはまだ式で変えているので、直すまでは確かめから外している
- 図のすべての要素に座標があり、`view_diagram` の一覧で、重なり（`overlaps`）と、線が要素の上を通るところ（`lines_through_elements`）がない
- 実際のデータ（`<モデル名>.data.csv`）があれば、読めて、列名がモデルの要素と合い、時刻がシミュレーションの期間と重なる（`import_data` と同じ確かめ方）

`tests/examples-numbers.test.ts` は、説明の要の数字が、シミュレーションの結果と合っているかを確かめる。モデルごとに 2〜4 つの数字（どのモデル・シナリオ・要素の、どの時刻の値か、最大値か、ある値を初めて下回る時刻か）を表に書いてあり、何も変えない実行と保存したシナリオを、モデルのシミュレーションの設定で動かして照らす。値の誤差は、書いた桁に合わせて 1% ほどまで許す。時刻（最大になる時刻、初めて下回る時刻）は、シミュレーションの刻みの半分未満の差しか許さない（1 刻みずれたら落ちる）。結果がずれたときは、どの sample のどの数字が、説明の値といくつ違うかを出して落ちる。表に書いた説明の言葉（`text`）が、説明に見つからないとき（説明の数字だけを変えたとき）も落ちる。表の行が 2 つより少ないか 4 つより多いモデルがあっても落ちる。

ループが原型どおりか、表にない数字、数字の妥当さなどは、テストでは確かめられないので、人が読んで確かめる。
