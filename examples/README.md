# sample のモデル

システム思考を学ぶための sample のモデル。システムダイナミクス（SD）を知っている人が、知らない人に見せて「問題を解くのに使える」と分かってもらうための教材にする。

どの sample も、身近な仕事の話を小さなモデルにしてある。図でフィードバックループ（R：強めるループ、B：釣り合わせるループ）を見て、グラフで動きを確かめ、シナリオで「どこを変えると効くか（てこ）」を比べる。

## 学ぶ順

上から順に見ると、前の sample で学んだことの上に、新しいことを 1 つずつ足していける。

### 0 コーヒーが冷める

- 学ぶこと：釣り合わせるループ（B）。差が縮むほど変化がゆっくりになり、目標（部屋の温度）に近づいて落ち着く。物理の法則（ニュートンの冷却の法則）なので、議論の余地がない。最初に見せる
- フォルダ：[0_コーヒーが冷める](0_コーヒーが冷める/)（coffee-cooling.json）

### 1 成長の限界

- 学ぶこと：強めるループ（R）と、R と B の組み合わせ（S 字の動き）
- フォルダ：[1_成長の限界](1_成長の限界/)（limits-to-growth.json）

### 2 うまくいかない解決策

- 学ぶこと：遅れ。目先はよくなり、後で悪くなる
- フォルダ：[2_うまくいかない解決策](2_うまくいかない解決策/)（fixes-that-fail.json）

### 3 問題のすり替わり

- 学ぶこと：対症療法が、根本の解決の力を奪う
- フォルダ：[3_問題のすり替わり](3_問題のすり替わり/)（shifting-the-burden.json）

### 4 エスカレート

- 学ぶこと：2 者の B がつながると、全体が R になる
- フォルダ：[4_エスカレート](4_エスカレート/)（price-war.json）

### 5 成長と投資不足

- 学ぶこと：1〜3 の組み合わせ。目標のなし崩し
- フォルダ：[5_成長と投資不足](5_成長と投資不足/)（growth-and-underinvestment.json）

### 6 ブルウィップ効果

- 学ぶこと：遅れが何段も重なると、振動する（ビールゲーム）。大きいので最後に見せる
- フォルダ：[6_ブルウィップ効果](6_ブルウィップ効果/)（bullwhip.json、対策を比べる bullwhip-countermeasures.json）

## 使い方

sample は npm パッケージには入っていない。[GitHub のリポジトリ](https://github.com/kagu3/loopsight) から取る（`git clone` するか、「Code」→「Download ZIP」で落として展開する）。

1. sample のフォルダ（例：`examples/1_成長の限界/`）を、フォルダごと作業フォルダにコピーする。作業フォルダは、MCP サーバーとビューアに渡しているフォルダ（[はじめての手順](../docs/getting-started.md) のとおりなら、ホームフォルダの中の `loopsight-models`）
2. ビューアのモデルの一覧に、フォルダと一緒に出てくる。開くと、図、グラフ、シナリオが見られる
3. Claude に、次のように頼める

> 1_成長の限界 のモデルの R と B のループを説明して、図で目立たせて。

> このモデルのシナリオを「元のモデル」と比べて、何が効いているのか説明して。

モデルの説明（ビューアと `get_model` で読める）は、「どんな問題か → どんな構造か → どんな動きになるか → てこはどこか」の順に書いてある。

## 出典と、数字について

1〜5 は、ピーター・センゲ『学習する組織』（原題 *The Fifth Discipline*）の「システムの原型」を、6 は同じ本のビールゲームをもとにした、このプロジェクトで作ったモデル。本の文章や図は写さず、筋書きだけを借りて、同じ構造の仕事の話に置き換えている。0 は物理の法則（ニュートンの冷却の法則）をもとにしている。

1〜6 の数字は、動きの形を見せるための仮の値で、実際の会社や仕事の値ではない。0 だけは例外で、物理の法則のモデルなので、実測にもとづく値を使っている（値の根拠は、そのモデルの説明に書いてある）。どの sample も、分かりやすくするために話を単純にしてある（何を省いたかは、各モデルの説明に書いてある）。

## sample を足す・直すときの決まり

### 置き方

- `examples/<番号>_<名前>/<英数字>.json` に置く（例：`examples/1_成長の限界/limits-to-growth.json`）。番号は上の「学ぶ順」の番号
- 実際のデータ（`<モデル名>.data.csv`）があれば、モデルと同じフォルダに置く
- 要素の名前、説明、シナリオは日本語で書く。モデルのファイル名は英数字と `_` `-` にする（例：`limits-to-growth.json`）
- sample を足したら、上の「学ぶ順」に項目を足し、「学ぶこと」と、フォルダへのリンクとモデルのファイル名を書く

  ```markdown
  - フォルダ：[1_成長の限界](1_成長の限界/)（limits-to-growth.json）
  ```

### 中身の決まり

- **簡単で、理論に穴がない（批判されにくい）こと。** ただし抽象的すぎず、仕事の具体的な話にする
- **式にするのは、裏付けのある関係だけ。** 物理や算数で決まること、研究で何度も確かめられたこと
- **人の判断は、判断の決まりは図に入れてよいが、どれだけ強く反応するかはシナリオのつまみにする。** 人の間違った反応と、てこ（効く打ち手）はシナリオで見せる
- **説明文は「どんな問題か → どんな構造か → どんな動きになるか → てこはどこか」の順。** 数字は動きの形を見せるための仮の値だと書く（0 のように実測にもとづく値を使うときは、その根拠を書く）。単純化したことも書く
- **てこのシナリオを 1 つ以上入れる。** 対策は図に足さず、シナリオか別のモデルで比べる
- **すべてのリンクに極性（`behavior.polarity`）を入れ、時間がたってから効くつながりには遅れの印（`display.delay`）を付ける。** `find_loops` で原型どおりの R と B が見つかるようにする
- **図に重なりや、線が要素の上を通るところがない**（`view_diagram` の一覧が空）
- **本の文章・図・固有名は写さない。** 筋書きは使ってよい。実在の会社や国の話は、同じ構造の仕事の話に置き換える。出典として本の名前を書くのはかまわない

### テストで確かめていること

`npm test`（`tests/examples.test.ts`）が、`examples/` の下のすべての ModelJSON（`*.json`）について次を確かめる。1 つでも守らないと、どの sample のどの決まりに反したかを出して落ちる。この README のリンク切れは `tests/docs-links.test.ts` が確かめる。

- 置き方が `examples/<番号>_<名前>/<英数字と _ ->.json` になっている
- 検証（`validate_model`、試しの実行あり）でエラーも警告もない
- モデルの説明（`description`）がある
- すべてのリンクに極性（+ か −）がある。`find_loops` で R か B か決まっていないループがない
- シナリオが 1 つ以上あり、「元のモデル」もシナリオもすべて実行できる
- 図のすべての要素に座標があり、`view_diagram` の一覧で、重なり（`overlaps`）と、線が要素の上を通るところ（`lines_through_elements`）がない

ループが原型どおりか、説明文の順番、数字の妥当さなどは、テストでは確かめられないので、人が読んで確かめる。
